# AI Company Phase 2: Complete Setup and User Guide

This guide is for both technical administrators and first-time business users. The project runs locally with FastAPI, SQL Server, SQLAlchemy, ODBC Driver 17, and a browser-based requirement workspace.

## 1. What this version includes

- Health check and SQL Server connectivity
- AI Agent registry listing
- Friendly browser UI at `http://127.0.0.1:8000/`
- Create, list, view and update requirements
- Send an existing requirement to the AI CEO for structured assessment
- Persist assessment evidence, involved departments and required skills
- Audit lifecycle actions using a Correlation ID
- API schema and interactive documentation are disabled on the public deployment.

## 2. Prerequisites

Install these before starting:

1. Windows 10 or Windows 11
2. SQL Server Developer Edition or an accessible local SQL Server instance
3. SQL Server Management Studio
4. Python 3.11 or newer
5. Microsoft ODBC Driver 17 for SQL Server

Confirm Python:

```cmd
python --version
```

Confirm the available ODBC driver:

```cmd
python -c "import pyodbc; print(pyodbc.drivers())"
```

The result must include:

```text
ODBC Driver 17 for SQL Server
```

## 4. Prepare the SQL Server database

If the original `AICompany` database and base tables already exist, run:

```text
sql\03_phase2_assessment.sql
sql\04_auth_user_role.sql
sql\05_manager_team_visibility.sql
sql\06_approval_notifications.sql
```

The assessment migration adds its tables without deleting existing requirements. The auth-role migration creates or enables the standard `USER` role and assigns it only to accounts whose existing role is missing or inactive; valid active roles, including privileged roles, are preserved. The manager migration adds an optional direct manager relationship and enables the `MANAGER` role; administrators must explicitly assign reporting relationships and roles.

Until an admin UI exists, an authorized database administrator can assign a direct reporting relationship with this checked transaction. Replace both example addresses, verify them, and retain change evidence:

```sql
USE AICompany;
GO
BEGIN TRANSACTION;
DECLARE @ManagerEmail nvarchar(255) = N'manager@company.example';
DECLARE @EmployeeEmail nvarchar(255) = N'employee@company.example';
DECLARE @ManagerID uniqueidentifier;
DECLARE @EmployeeID uniqueidentifier;

SELECT @ManagerID = UserID FROM dbo.AppUser WHERE Email = @ManagerEmail AND IsActive = 1;
SELECT @EmployeeID = UserID FROM dbo.AppUser WHERE Email = @EmployeeEmail AND IsActive = 1;
IF @ManagerID IS NULL OR @EmployeeID IS NULL THROW 51010, 'Both active accounts must exist.', 1;

UPDATE dbo.AppUser SET ManagerUserID = @ManagerID WHERE UserID = @EmployeeID;
UPDATE dbo.AppUser
SET RoleID = (SELECT TOP (1) RoleID FROM dbo.Role WHERE RoleCode = 'MANAGER' AND IsActive = 1)
WHERE UserID = @ManagerID;
COMMIT TRANSACTION;
GO
```

Manager access is currently direct-report only; nested management hierarchies and an administrative assignment UI are not implemented.

The approval migration adds the durable in-app notification table and approval decision timestamp. It is safe to rerun.

For Phase 7 workforce reuse, after the existing workforce schema migrations through `sql\23_single_organization_rbac.sql`, run `sql\24_intelligent_workforce_reuse.sql`. It creates the auditable reuse-assessment table used by the Workforce Manager review queue and its metrics. Do not enable the Phase 7 routes before this migration is applied.

If starting from a completely new environment, first run the original base scripts:

1. `01_create_database.sql`
2. `01_seed.sql`
3. `sql\03_phase2_assessment.sql`
4. `sql\04_auth_user_role.sql`
5. `sql\05_manager_team_visibility.sql`
6. `sql\06_approval_notifications.sql`

After the migration, verify:

USE AICompany;

## 5. Configure the application

Copy `.env.example` and rename the copy to `.env`.

Default configuration:

```env
DATABASE_URL=mssql+pyodbc://@localhost/AICompany?driver=ODBC+Driver+17+for+SQL+Server&trusted_connection=yes&TrustServerCertificate=yes
JWT_SECRET_KEY=GENERATE_A_RANDOM_SECRET_WITH_AT_LEAST_32_CHARACTERS
```

Replace the placeholder with a unique random value generated by `python -c "import secrets; print(secrets.token_urlsafe(48))"`. Keep the actual value in the untracked `.env` file only; never add it to source control or share it in screenshots.

If SQL Server uses a named instance, replace `localhost` with the exact instance. Example:

```env
DATABASE_URL=mssql+pyodbc://@localhost\SQLEXPRESS/AICompany?driver=ODBC+Driver+17+for+SQL+Server&trusted_connection=yes&TrustServerCertificate=yes
```

## 8. How to gather a requirement in guided chat

1. Open `http://127.0.0.1:8000/static/requirement-chat.html`, or choose **Describe a requirement** on the landing page.
2. Answer the AI CEO intake assistant's questions about the business problem, expected outcome, users/stakeholders, systems/data, constraints/security, and timing/dependencies.
3. The intake may ask extra follow-up questions when your answers mention an integration or personal/sensitive data. These follow-ups are keyword-driven in the current MVP.
4. The live brief on the right shows the captured answers. Add final context in the chat if needed.
5. Choose Low, Medium, High, or Critical urgency. The choice is a request priority, not a risk determination or approval.
6. Review the summary and select **Submit requirement**. The brief is not saved before submission.
7. Low/Medium requests are saved for the requirement workflow. High/Critical requests are saved and then automatically sent to the current AI CEO assessment endpoint.
8. After submission, note the requirement ID and status shown in the conversation.

Do not enter passwords, payment card data, secrets, or real personal records. Provide categories and access requirements instead.

The current chat is a guided scripted experience; it does not call an LLM or retain draft conversation server-side. The current AI CEO provider is deterministic. Treat assessment output as advisory, not as approval to spend or begin delivery.

## 9. How a requirement is stored

The chat currently maps the conversation to the existing API contract:

- Title: a shortened summary of the first business-problem answer.
- Description: labeled sections containing problem, outcome, stakeholders, systems, constraints, timing, conditional clarifications, and final context.
- Requested by: the display name from the locally available JWT when readable, otherwise `Business User`.
- Priority: the user's Low/Medium/High/Critical selection.

The browser sends `POST /requirements`. The API returns the requirement ID, status, and timestamps. The current API does not persist each chat turn as a separate record, and authentication/authorization on this endpoint must be hardened before production.

## 10. High and Critical automatic assessment

For High or Critical priority, the browser invokes `POST /requirements/{id}/assess` after the requirement is saved. If assessment fails, the requirement remains saved and the page offers a retry. Do not submit again to retry assessment, because that would create a second requirement.

The assessment result may include classification, business domain, complexity, risk, feasibility, confidence, summary, assumptions, constraints, risks, departments, and skills. The current deterministic provider is a development placeholder and its fixed output may not accurately reflect an individual request. High/Critical priority does not itself imply a risk level, an approval record, or authorization for delivery.

## 11. How to track a request

1. Sign in and open `http://127.0.0.1:8000/requests`, or choose **My requests** from the workspace navigation.
2. Select a request to see its recorded stage: submitted, AI CEO assessment, human approval, or project delivery.
3. Review the next-action message, assessment summary, approval records, linked project status, and recorded audit events.
4. Refresh after a workflow update. The list is scoped to requests created by the signed-in user; Owner/Super Admin can inspect all currently stored requests.

The tracker displays persisted records only. If approval is required but not assigned, or a request is approved without a linked project, it reports that gap instead of implying the next step occurred. Audit details appear only when the current services recorded them.

## 12. Review and decide approvals

1. Sign in as an assigned approver or Owner/Super Admin and open `/approval-center`.
2. Select a pending approval and review the linked request, priority, and approval stage.
3. Enter a decision reason of at least five characters.
4. Choose **Approve**, **Request information**, or **Reject**. Every decision is audited.
5. If other approval records remain pending, delivery does not continue. After the final approval for the stage, the request becomes Approved and one Planned project plus seven Planned tasks are created idempotently.
6. Rejection closes the request and creates no project. Requesting information sets the request to InformationRequired and blocks project creation.

Approvers receive in-app notifications. The current MVP does not send email, SMS, or push notifications and does not activate task execution/deployment.

## 13. Existing requirement management and manual assessment

The earlier form at `/` can still be used to list, search, edit eligible pre-execution requirements, and manually request assessment. Editing is currently allowed for Submitted, Assessed, AssessmentFailed, and InformationRequired statuses. The chat is the recommended path for new business requests.

The underlying assessment flow locks the requirement, loads the active AI CEO record, creates a correlation ID, validates provider output, applies current policy rules, writes assessment evidence, updates requirement status, and records audit events. Human-review-required assessments now create an approval record and in-app notifications; the Approval Center records reasoned decisions and continues only after the last required approval. A `PendingApproval` label is not proof of completion; check the approval record and tracker evidence.

### Current AI CEO intake assistant prompt

The browser follows a scripted prompt sequence in `app/static/requirement-chat.js`. The governed production agent should use the prompt contract in `docs/Requirement_Management.md` and must not claim that it can approve or execute work.

## 14. Verify data in SQL Server

Latest requirements:

```sql
SELECT TOP 20 *
FROM dbo.Requirement
ORDER BY CreatedAtUtc DESC;
```

Latest assessments:

```sql
SELECT TOP 20 *
FROM dbo.RequirementAssessment
ORDER BY CreatedAtUtc DESC;
```

Departments selected for assessments:

```sql
SELECT
    ra.RequirementID,
    d.DepartmentName,
    rad.Responsibility,
    rad.IsLeadDepartment,
    rad.Priority,
    rad.Status
FROM dbo.RequirementAssessmentDepartment rad
JOIN dbo.RequirementAssessment ra
    ON ra.RequirementAssessmentID = rad.RequirementAssessmentID
JOIN dbo.Department d
    ON d.DepartmentID = rad.DepartmentID
ORDER BY ra.CreatedAtUtc DESC;
```

Required skills:

```sql
SELECT
    rs.RequirementID,
    s.Name AS SkillName,
    rs.Priority,
    rs.MinimumProficiency,
    rs.SkillPurpose,
    rs.EstimatedEffortHours,
    rs.IsMandatory
FROM dbo.RequirementSkill rs
JOIN dbo.Skill s
    ON s.SkillID = rs.SkillID;
```

Audit history:

```sql
SELECT TOP 100 *
FROM dbo.AuditLog
ORDER BY CreatedAtUtc DESC;
```

## 16. Troubleshooting

### Health returns 500

Check the command-window traceback. Confirm the installed driver and `.env` connection string both use `ODBC Driver 17 for SQL Server`.

### Database login or server not found

Confirm the exact server name in SSMS. If it is `localhost\SQLEXPRESS`, use the same instance in `.env`.

### Assessment endpoint is missing

Stop and restart FastAPI after replacing the project files:

```cmd
Ctrl+C
run_local.bat
```

Refresh Swagger using `Ctrl+F5`.

### Requirement assessment returns a duplicate/version issue

Send `force_reassessment` as true. Each assessment uses a new version number.

### UI appears old after an update

Use `Ctrl+F5` or clear the browser cache.

## 17. Security and project-data boundary

- The landing page, sign-in, and registration screens are public. Workspace pages and business-data APIs require an authenticated session.
- The session is held in an HttpOnly, SameSite=Strict cookie. Session tokens are not stored in localStorage.
- Ordinary users are scoped to requirements they created. Projects, approvals, agent registry, and company-wide dashboard values are restricted to Owner/Super Admin roles.
- Public API schema/docs are disabled. `/health` returns only a liveness signal; `/ready` reports readiness without database/server names.
- Static serving is allowlisted to UI assets. Browser-delivered HTML/CSS/JavaScript is inherently inspectable; never put secrets, server code, or actual project records in frontend assets. Protect data at server/API boundaries, not with CSS or client-side masking.
- Configure a unique random `JWT_SECRET_KEY` of at least 32 characters in the untracked `.env`. Changing it invalidates existing sessions.
- New passwords are PBKDF2-hashed. Existing plaintext passwords are upgraded on successful login; rotate legacy credentials and migrate all existing users before production.

This remains an MVP. Before production, add tenant/company membership enforcement, database-controlled Owner bootstrap, MFA, rate limiting and login-abuse detection, robust CSRF protection, HTTPS-only cookies, managed secrets, audit retention, backup/recovery, and security testing. Existing records do not all carry company ownership; cross-user project data therefore remains Owner-only until tenant isolation is implemented and verified.

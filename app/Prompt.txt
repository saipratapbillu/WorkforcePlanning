SECURITY CONTINUATION RULES (2026-10-22)
=========================================================

- Treat source code, project information, requirements, assessments, users, approvals, agents, and operational metrics as private by default.
- Public routes are limited to marketing, login, registration, liveness, and allowlisted presentation assets. Private pages and every business-data API require server-side authentication and authorization.
- The frontend cannot conceal HTML, CSS, or JavaScript delivered to a browser. Never put credentials, signing keys, server implementation, or actual customer/project data in public client assets. Protect project data at backend routes and database queries, not by hiding UI elements or masking DOM text.
- Keep session material in an HttpOnly, SameSite cookie; do not move JWTs back into localStorage or URLs. Validate signature, issuer, audience, expiry, active user, and current database role on every request.
- Ordinary users may access only their own requirements. Cross-user project, approval, agent-registry, and aggregate data is Owner/Super Admin-only until company membership and tenant scoping have been implemented and tested.
- Request visibility policy: USER sees own requests; MANAGER sees own plus explicitly assigned direct reports via `ManagerUserID`; ADMIN sees all company request flows but does not automatically gain Owner-only approval authority; OWNER/SUPER_ADMIN have company-wide visibility and designated governance authority.
- Every pending approval must notify its assigned approver. Critical/overdue approval notifications also go to Owner/Super Admin oversight recipients. Do not broadcast sensitive requirement content to unrelated users.
- When a valid approval is recorded, the workflow engine should automatically enqueue the next eligible workflow stage exactly once, only after every required approval passes and no rejection, information request, security hold, or policy block remains. Project/task generation must be idempotent and audited. Never claim this automation exists until implemented and tested.
- Voice assistant and voice approval are future capabilities. Voice alone must never authorize consequential actions; require authenticated identity, step-up MFA, read-back confirmation of the exact decision, replay/deepfake controls, audit evidence, privacy retention rules, and a non-voice alternative.
- Voice capabilities remain roadmap-only. Do not add voice-based approval until the identity, consent, transaction read-back, replay/deepfake threat model, audit evidence, retention policy, and manual fallback gates are implemented and independently tested.
- API schemas/docs must remain disabled publicly. Health responses must not reveal database names, server names, secrets, filesystem paths, environment values, or stack traces.
- Never log passwords, tokens, cookies, secrets, requirement bodies, or assessment payloads unnecessarily. Secrets are environment/secret-store configuration only and never committed.
- Continue with defense in depth: password hashing, same-origin/CSRF protections, login rate limiting, MFA, immutable audit events, tenant-isolation tests, and a controlled Owner bootstrap. A UI role badge is not authorization.
- In every future feature, document exactly which routes are public, which require login, the role/tenant rules, data returned, audit trail, and tests proving anonymous and unauthorized requests are denied.
